Medical College HRM Integration Document

1. Purpose

This document explains how the Human Resource Management (HRM) module is connected with the Finance and Education modules in the Medical College system built on Frappe/ERPNext/HRMS/Education. It is intended for developers of other modules so they can continue implementation using the same integration logic, ownership rules, and data flow assumptions.

2. Scope

The current HRM solution covers:

  • Core employee master data
  • Faculty/instructor linkage
  • Saudi Ministry of Education (Jameah) compliance fields
  • Organizational placement structure
  • Facility assignment
  • Qualifications, experience, training, publications, and awards
Important: The architectural rule is that customizations are stored in the custom app medical_hrms, without modifying core frappe, erpnext, hrms, or education logic directly.

3. System Role Ownership

Area Primary Module System of Record Notes
Employee identity and employment lifecycle HRM Employee HR owns hiring, status, assignment, personal and employment data.
Teaching/faculty academic profile Education Instructor Academic operations use Instructor, but linked to Employee for HR consistency.

5. HRM to Education Module Integration

5.1 Why the integration exists

In a Medical College environment, many employees are also faculty members. HR must manage them as employees, while the Education module must manage them as instructors for academic scheduling, teaching, and reporting.

5.2 Integration model

HRM Side Education Side Integration Purpose
Employee Instructor One faculty member may exist as both an employee and an instructor.
Jameah demographic fields Mirrored on Instructor Ensures ministry-required faculty reporting can be done from academic records.
Jameah institute placement Mirrored on Instructor Keeps faculty organizational placement visible in Education workflows.
Facility assignment Visible for Instructor Supports academic and clinical assignment visibility.
Qualifications/training/publications Mirrored child tables Supports faculty accreditation, promotion, and academic reporting.

5.3 Data flow principles

  • HRM owns employment identity: employee lifecycle, joining, payroll relevance, and core employment data.
  • Education owns teaching operations: academic usage of faculty profile inside class, exam, or instructor workflows.
  • Shared ministry fields must remain aligned: demographic and ministry-compliance fields should not diverge between Employee and Instructor.
  • Lookup values must stay controlled: any lookup must come from predefined master data, not free text.

5.4 Developer handoff guidance for Education team

  • Use the linked Employee record as the employment source of truth.
  • Do not create parallel free-text academic demographic fields when a mapped Jameah field already exists.
  • If new academic forms need nationality, specialization, rank, or faculty status, link to existing masters.
  • If a faculty workflow changes organizational placement, confirm whether Employee must also be updated.

6. HRM to Finance Module Integration

6.1 Why the integration exists

HRM produces the people, status, attendance, leave, and employment context that Finance needs to process payroll, allowances, deductions, and accounting entries.

6.2 Integration model

HRM Component Finance Component Integration Purpose
Employee Salary Structure Assignment Finance uses employee master and employment status to determine payroll eligibility.
Attendance / Leave / Shift data Salary Slip Affects payable days, leave deductions, and overtime calculations.
HR allowances and requests Additional Salary / payroll components Approved HR benefits may become payroll earnings or deductions.
Employee department / designation / company Payroll Entry, costing, reporting Used for grouping, approvals, budget checks, and reporting.
Employment status changes Salary generation controls Inactive or separated employees should not continue into payroll.

6.3 Expected Finance touchpoints

  • Monthly payroll processing
  • Allowances and benefits
  • Overtime and special compensation
  • End-of-service settlement inputs
  • Department-wise salary reporting
  • Budget and cost-center level staffing analysis

6.4 Developer handoff guidance for Finance team

  • Treat HR employee status as a controlling input for payroll eligibility.
  • Reuse HRM assignment fields like department, designation, and facility when reporting requires organizational breakdown.
  • If a new finance workflow depends on faculty role, use the Employee-to-Instructor link instead of duplicating faculty logic.
  • Where ministry reporting affects compensation classification, rely on controlled masters rather than text fields.

7. Shared Master Data Used Across Modules

Master Data Used By Purpose
Jameah Ministry Code HRM, Education Controlled ministry values such as nationality, city, degree, specialization, identity type.
Jameah Branch HRM, Education, reporting Formal university branch placement.
Jameah College HRM, Education College placement for faculty and staff.
Jameah Academic Department HRM, Education Academic departmental assignment.
Jameah Facility HRM, Education, possible operations Hospital/clinic/lab/classroom assignment and reporting.

8. Recommended Integration Rules for Developers

  1. Do not duplicate employee identity logic in Finance or Education.
  2. Use Employee as the primary HR record.
  3. Use Instructor as the academic operational profile for faculty.
  4. Use linked masters for all controlled values.
  5. Do not introduce free-text lookups for ministry-mapped fields.
  6. Keep organization and facility references consistent across HR and Education.
  7. When new modules need staff/faculty data, integrate through existing doctypes before creating new structures.

10. Next Development Recommendations

  • Create formal synchronization rules between Employee and Instructor for shared fields.
  • Publish a field mapping sheet showing which module owns each field.
  • Standardize API/service methods for reading faculty identity and placement.
  • Introduce validation so Finance and Education cannot use invalid free-text ministry values.
  • Document event triggers for onboarding, faculty creation, transfer, and separation.

11. Conclusion

The HRM module is the employment and compliance foundation of the Medical College system. The Education module depends on HRM for faculty identity and institutional placement, while the Finance module depends on HRM for payroll eligibility, organizational assignment, and compensation context.

For future development, all module teams should integrate with the existing Employee, Instructor, and Jameah master structures instead of creating parallel data models.
